## Problem

Every canonical entity, relationship, evidence record, change set and snapshot needs an Atlas-owned identifier. It must have these properties:

- it never changes (renames, re-parenting, taxonomy upgrades);
- it is opaque in API paths and reveals no provider structure;
- it is cheap to index in PostgreSQL 15;
- it is generated without coordination (application, loader, future connectors).

Provider-native identifiers (Azure Resource IDs, Kubernetes UIDs, APIM IDs) are **separate** and handled by ADR-0003. They are never used as the canonical ID, because they change on moves and recreation, and they leak tenant and subscription structure.

## Options

| Option | For | Against |
|---|---|---|
| **A. UUIDv7 in a native `uuid` column, generated in the application** (recommended) | Time-ordered: new rows append to the B-tree, with less page splitting and better cache locality than random UUIDs at 100k+ rows. 16 bytes, native type, standard (RFC 9562). Already used for correlation and run IDs (`atlas.core.ids.uuid7`, ATLAS-001) | Embeds creation time at millisecond resolution (minor disclosure); PostgreSQL 15 has no built-in v7 generator, so the database cannot default it |
| B. UUIDv4 | No time disclosure; `gen_random_uuid()` built in | Random inserts fragment indexes; no natural ordering |
| C. `bigint` sequence plus a public UUID | Smallest internal keys and joins | Two identifiers per row and every FK on the internal key, plus mapping on every API boundary; sequences are per database, which complicates a future organization move |
| D. ULID or other text IDs | Sortable and readable | Text storage (26+ bytes) and slower comparisons, plus a non-native type and custom validation |

## Recommendation

**Option A.**

1. All Atlas-owned primary keys are UUIDv7 in PostgreSQL `uuid` columns, generated by `atlas.core.ids.uuid7()`. No database default, so a missing ID fails loudly.
2. IDs are **immutable** and **never reused**:
   - a merged entity keeps its ID as a tombstone that points to the survivor (ADR-0003);
   - a deleted entity keeps its ID as a tombstone (INV-06).
3. API paths and payloads use the canonical lowercase hyphenated form. Clients treat it as opaque and never parse time from it.
4. Fixtures carry **explicit, pre-generated** UUIDv7 literals, so repeated loads produce identical IDs (deterministic loading, ADR-0008). No UUIDv5/name-derived canonical IDs: a name must never determine identity.
5. Ordering by ID is allowed only as a tiebreaker. Business ordering uses explicit columns (revision, timestamps).

## Trade-offs and risks

- **Creation-time disclosure:** an ID reveals roughly when an entity was created. Atlas IDs are only shown to authorized users, and hidden entities are never returned (anti-enumeration, DEC-035). Accepted.
- **Clock skew between generators** only affects ordering, never uniqueness: 74 random bits per millisecond.
- **Monotonicity within a millisecond** is not guaranteed by the current generator. Nothing may depend on it.

## Impact on the database schema

`id uuid PRIMARY KEY` (plus `UNIQUE (org_id, id)` for composite foreign keys, ADR-0016) on canonical tables.

## Impact on APIs and authorization

- The contract declares IDs as `string`, `format: uuid`, and documents them as opaque.
- The existence of an ID is never confirmed to an unauthorized caller (404 policy).

## Migration and compatibility

- Nothing to migrate: no canonical data exists yet.
- Changing the ID scheme later would touch every FK, so this is a one-way decision in practice. It is also fully compatible with option B values, which are also UUIDs, should a source ever need v4.

## Approved by the owner (25 Oct 2026)

1. UUIDv7, native `uuid`, application-generated, immutable, never reused.
2. Fixtures carry explicit IDs; no name-derived canonical IDs.
